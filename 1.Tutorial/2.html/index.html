AWS Tutorial 02

S3로 정적 웹사이트 호스팅하기

HTML 파일 하나를 인터넷에 공개하는 가장 단순한 방법이다. 서버를 한 대도 띄우지 않고, AWS 콘솔에서 클릭 몇 번으로 배포한다.

소요 15분 AWS 콘솔 서버 불필요

시작하기 전에

  • 로그인 가능한 AWS 계정
  • 업로드할 index.html 파일 (이 페이지 파일을 그대로 써도 된다)
  • 작업할 리전을 하나 정해 둔다 — 모든 실습은 버지니아 북부 리전 us-east-1을 사용한다
이 실습의 방침

여기서는 버킷을 퍼블릭으로 열어 배포한다. S3가 어떻게 웹사이트를 서빙하는지 가장 적은 단계로 보여 주기 위해서다. 실무 배포 방식은 마지막 이론 섹션에서 따로 다룬다.

단계별 실습

1

S3 버킷 만들기

AWS 콘솔 상단 검색창에 S3를 입력해 이동한 뒤 [버킷 만들기]를 누른다. 리전이 미국 동부(버지니아 북부) us-east-1인지 확인한다.

버킷 이름 규칙 — 여기서 가장 많이 막힌다
  • 전 세계에서 유일해야 한다. 이미 남이 쓰는 이름은 만들 수 없다.
  • 영문 소문자·숫자·하이픈(-)·마침표(.)만 쓸 수 있다. 대문자와 밑줄(_)은 불가다.
  • 3자 이상 63자 이하, 시작과 끝은 소문자 또는 숫자여야 한다.
  • IP 주소 형태(192.168.0.1)는 쓸 수 없다.

권장 형태: 이름-학번-s3 → hong-2024001-s3

나머지 설정은 기본값 그대로 두고 [버킷 만들기]로 생성을 마친다.

2

퍼블릭 액세스 차단 해제

새 버킷은 기본적으로 모든 공개 접근이 막혀 있다. 웹사이트로 쓰려면 이 잠금을 풀어야 한다.

  • 방금 만든 버킷 이름을 클릭해 들어간다.
  • [권한] 탭 → [퍼블릭 액세스 차단(버킷 설정)]의 [편집]을 누른다.
  • 모든 퍼블릭 액세스 차단 체크를 해제하고 저장한다.
  • 확인창에 확인을 입력해 승인한다.
주의

이 순간부터 이 버킷에 올린 파일은 인터넷 누구나 볼 수 있다. 개인정보·자격 증명·과제 원본 같은 파일은 절대 올리지 않는다.

3

버킷 정책으로 읽기 권한 부여

차단을 푼 것만으로는 부족하다. "누가 무엇을 할 수 있는지"를 버킷 정책으로 명시해야 한다.

  • [권한] 탭 → [버킷 정책]의 [편집]을 누른다.
  • 아래 JSON을 붙여넣고, your-bucket-name을 내 버킷 이름으로 바꾼다.
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "PublicReadGetObject",
      "Effect": "Allow",
      "Principal": "*",
      "Action": "s3:GetObject",
      "Resource": "arn:aws:s3:::your-bucket-name/*"
    }
  ]
}
읽는 법
  • "Principal": "*" — 누구나(익명 사용자 포함)
  • "Action": "s3:GetObject" — 객체를 읽는 것만 허용. 업로드·삭제는 불가
  • Resource 끝의 /* — 버킷 안의 모든 객체가 대상. 이 /*를 빼먹으면 정책이 동작하지 않는다
4

정적 웹사이트 호스팅 활성화

  • [속성] 탭으로 이동해 맨 아래 [정적 웹 사이트 호스팅]의 [편집]을 누른다.
  • 활성화를 선택한다.
  • 호스팅 유형은 정적 웹 사이트 호스팅을 고른다.
  • 인덱스 문서에 index.html을 입력한다.
  • 오류 문서는 비워 두어도 되고, error.html을 넣어도 된다.

저장하면 버킷 웹 사이트 엔드포인트 주소가 생긴다. 6단계에서 다시 확인한다.

5

index.html 업로드

  • [객체] 탭 → [업로드] → [파일 추가]를 누른다.
  • index.html을 선택하고 [업로드]를 누른다.
  • 파일은 반드시 버킷 최상위(루트)에 있어야 한다. 폴더 안에 넣으면 인덱스 문서로 인식되지 않는다.

CSS·이미지 등 다른 파일이 있다면 HTML에서 참조하는 경로 구조 그대로 함께 올린다.

6

엔드포인트로 접속 확인

  • [속성] 탭 → [정적 웹 사이트 호스팅] 섹션의 링크를 클릭한다.
  • 주소 형식은 다음과 같다.
http://버킷이름.s3-website-us-east-1.amazonaws.com
잘 안 될 때
  • 403 Forbidden — 2단계 차단 해제 또는 3단계 버킷 정책을 다시 확인한다. 정책의 Resource에 버킷 이름이 정확히 들어갔는지, 끝에 /*가 있는지 본다.
  • 404 Not Found — 파일 이름이 index.html이 맞는지, 루트에 있는지, 4단계에 입력한 인덱스 문서 이름과 같은지 본다.
  • 주소가 https로 열리지 않음 — 정상이다. S3 웹사이트 엔드포인트는 http만 지원한다. HTTPS는 아래 이론 섹션의 CloudFront가 필요하다.

완료

이제 내 웹사이트가 인터넷에 공개됐다. 주소를 공유하면 누구나 접속할 수 있다. index.html을 고쳐서 다시 업로드하면 즉시 반영된다.

실습이 끝나면

비용과 노출을 줄이기 위해 버킷의 객체를 모두 삭제한 뒤 버킷을 삭제한다. S3는 버킷이 비어 있어야 삭제된다.

이론 · 실습 없음

실무에서는: CloudFront + OAC

방금 한 방식은 배우기엔 좋지만 실제 서비스에는 쓰지 않는다. 실무에서는 S3 버킷을 비공개로 두고, 그 앞에 CDN인 CloudFront를 세운다. 여기서는 개념만 이해하고 넘어간다 — 이 섹션에 실습 단계는 없다.

퍼블릭 버킷의 문제

  • 버킷 주소가 그대로 노출된다. 누구나 S3 엔드포인트에 직접 접근할 수 있고, 정책을 한 줄만 잘못 쓰면 의도치 않은 파일까지 공개된다.
  • HTTPS를 쓸 수 없다. S3 웹사이트 엔드포인트는 http 전용이라 브라우저가 "안전하지 않음"으로 표시한다. 커스텀 도메인 인증서도 붙일 수 없다.
  • 매 요청이 S3까지 간다. 캐시가 없으니 같은 파일을 만 번 요청하면 만 번 모두 S3 요청 요금과 전송 요금이 발생하고, 멀리 있는 사용자일수록 느리다.

CloudFront가 바꾸는 것

  • 비공개 버킷 유지 — 퍼블릭 액세스 차단을 켜 둔 채로 배포한다. 버킷 정책은 Principal: "*" 대신 특정 CloudFront 배포에만 읽기를 허용한다. 사용자는 S3 주소를 알 수도, 쓸 수도 없다.
  • HTTPS 기본 제공 — CloudFront 도메인은 처음부터 https다. ACM 인증서를 붙이면 내 도메인에도 무료로 HTTPS를 적용할 수 있다.
  • 엣지 캐싱 — 전 세계 엣지 로케이션이 파일을 복사해 두고 대신 응답한다. 사용자에게 가까운 곳에서 응답하니 빠르고, S3까지 도달하는 요청 수가 줄어 비용도 내려간다.

OAC(Origin Access Control)란

"비공개 버킷인데 CloudFront는 어떻게 읽지?"에 대한 답이 OAC다. CloudFront가 S3에 요청을 보낼 때 서명된 신원을 함께 붙이고, 버킷 정책은 그 신원만 통과시킨다. 결과적으로 정문(CloudFront)은 열려 있고 뒷문(S3)은 잠겨 있는 구조가 된다.

요청 흐름

브라우저 → CloudFront 엣지 → (캐시에 있으면 여기서 바로 응답) → 없으면 OAC 서명을 붙여 비공개 S3 버킷에서 원본을 가져온 뒤 캐시에 저장하고 응답

예전에는 같은 목적으로 OAI(Origin Access Identity)를 썼다. 지금은 OAC가 후속 방식이며, 신규 배포에는 OAC를 쓰는 것이 권장된다.

정리

  • 학습·프로토타입 — 이 문서의 퍼블릭 S3 방식. 단계가 적고 결과를 바로 본다.
  • 실제 서비스 — 비공개 S3 + CloudFront + OAC. 보안·HTTPS·성능·비용을 한 번에 해결한다.

CloudFront 실습은 뒤쪽 수업에서 다룬다. 지금은 "퍼블릭 버킷은 실습용"이라는 것만 기억하면 된다.
